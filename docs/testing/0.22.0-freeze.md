### Recovery boundaries and a confirmed limitation

`apps/cli/test/image-crash.test.ts` uses an actual daemon/worker, real durable intent, an independent
loopback provider counter, `SIGKILL`, and restart of the same home without reseeding:

1. **Request received; provider reply withheld:** intent remains `uncertain`, there is no Result,
   startup sends no new image request, and exact-operation readmission refuses regeneration.
2. **Image bytes committed; worker IPC reply withheld:** completion and bytes survive the kill
   atomically and remain private. On restart, existing Results cleanup tombstones the abandoned,
   never-authorized bytes. The completed operation is retained, its tombstoned Result cannot be
   read or regenerated, and preview is refused. **A paid output could be lost in this window.**

The second case is not proof of recoverable image delivery. It confirms the existing private-byte
retention/disclosure policy; retain this limitation in release notes and review it before release.
Separately, all six already-authorized images remain downloadable byte-for-byte after a real restart.
No charge reversal, exactly-once external execution, live-provider crash behavior or durability
under every possible power-loss/storage failure is claimed.

While developing these tests, the harness incorrectly expected successful cleanup rows to remain,
and initially attached its IPC barrier at the wrong Node method. Both fixture defects were corrected.
An initial full-suite run also exceeded the image journey's old 30-second timeout while the upgrade
matrix and repeated crash runs competed for the same host. The expanded six-turn/restart journey
now has an explicit 60-second test budget; other tests and product deadlines are unchanged. The
subsequent full run passed. Initial failure: `/tmp/baz059-freeze-full-initial-timeout.log`.

### Version transition (re-rehearsed 2026-09-21 for the 0.22.0 retarget)

The original seeded recipe below **stands** — with a verified tail that strips the suffix. Two
shortcuts were rehearsed and **rejected**: running `changeset version` in pre mode unseeded plans
`0.21.0-beta.6`; exiting pre mode first strips `0.21.0-beta.5` to `0.21.0` while **consuming the
pending changesets unapplied** (mis-attributing them to the 0.21 line). The verified recipe, in a
disposable copy (`/tmp/baz022-rehearsal2`):

1. Seed commit: set the three public packages to unpublished `0.22.0-beta.0`; set `pre.json`
   `initialVersions` to the published `0.21.0-beta.5` baseline and empty its consumed
   `changesets` list.
2. `changeset version` (GitHub changelog active) — consumes the four candidate changesets with
   correct attribution, producing `0.22.0-beta.1`.
3. `changeset pre exit`, then `changeset version` again — strips the suffix to **exactly
   `0.22.0`** in all three public packages and deletes `pre.json`. Fix the changelog header if it
   still reads beta.1.

Steps 2–3 were executed for real in the scratch copy (changelog plugin disabled there only for
network reasons). The real sequence goes into the reviewed version PR.
