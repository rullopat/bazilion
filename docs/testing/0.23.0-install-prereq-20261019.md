## One candidate availability check, not a normal-install pass

A complete **1,139-path frozen core** was verified and its present files copied to a disposable
candidate tree, without operator configs/credentials or ignored source state. The existing pnpm v11
store was cloned using Btrfs copy-on-write (`cp -a --reflink=always`), not writable hardlinks to the
original cache. Its index inode was verified distinct. Existing v10/v11 cache sizes were observed
as4.2/4.1GiB; size alone says nothing about dependency or metadata completeness. The original store
was not mounted into the install namespace.

In a scrubbed private user/network/PID/proc namespace with disposable HOME/TMP/cache, read-only
system/installed Node24.20.0/pnpm12.14.0, DEVNULL stdin and no original source/home mounted, ran:

```sh
pnpm install --offline --ignore-scripts --frozen-lockfile --store-dir=/evidence/store
```

**Exit1.** After attempting supply-chain validation of1,068 lock entries, pnpm reported:

```text
ERR_PNPM_META_FETCH_FAIL
ERR_PNPM_NO_OFFLINE_META: Failed to resolve @aws-sdk/credential-provider-process
.../cache/pnpm/v12/metadata-full/https%3A+registry.npmjs.org/@aws-sdk/credential-provider-process.jsonl
```

That exact required v12 metadata file is also absent from the existing public-registry cache.
This is an unavailable offline validation prerequisite, **not** proof of a malicious package, a
successful policy check or an inventory of missing tarballs. No policy was disabled, cached registry
metadata synthesized, compatibility adapter added or network enabled. Lifecycle scripts were
explicitly disabled: none was run/qualified. The frozen candidate core and original lockfile stayed
byte-identical after failure.
