## Retention fix

`scripts/security-acceptance.mjs` now uses `scripts/testing/security-report.mjs` to allocate a
unique mode-0700 temporary directory and `report.json`. Only successful execution **and** existing
report validation remove that directory. A failing executor, missing/malformed/failed report or
other error preserves the directory and rethrows the original failure; a logging exception cannot
replace it. The message says **directory retained**, not that a report necessarily exists.
Random directories prevent PID-namespace PID reuse from overwriting an earlier failure.

The actual Vitest run arguments, required-case/status loop and `report.success` check are
byte-identical to the existing gate body. Manifest selection/collection assertions are unchanged.
No timeout, required case, product redaction, image dispatch or ownership policy changed.
Reports remain local to the private temporary directory; no automatic external artifact upload or
new disclosure path is added. Ephemeral CI-runner lifetime is not durable external retention.

**Nine Node 24.20.0 offline tests passed, zero failures/skips**, with scoped Biome and syntax checks
passing. Six helper tests cover success, partial/missing/malformed reports, distinct report paths,
private mode and logging failure. Three integration tests invoke the actual gate with a **fake pnpm
executor** to prove executor failure, validation failure and success cleanup. Those three tests
are orchestration evidence, **not** 366 real security-case passes. The security CI job runs these
small offline tests before the real gate; no remote CI result is claimed.

## Bounded diagnostic: two actual samples, then stop

Both samples used Node **24.20.0**, pnpm **12.14.0**, scrubbed private network/PID/proc namespaces,
read-only product source/system and the existing private ABI137 SQLite build mounted read-only.
Each received a separate initially empty disposable HOME/TMP/application-cache tree and retained
disposable-daemon stderr. No original home/account/daemon/Team, shared native binary, Docker engine,
network service or machine cache was changed; no install/download/live-provider request occurred.
“Cold” here means fresh **application directories**, not a cold OS/page cache.

A temporary sequencer imports the checked-in Vitest configuration unchanged and controls only the
two selected files' order. The original 15-second image barrier and 30-second test/hook settings
remain. Hashes prove both image test files and the security manifest stayed byte-identical through
this work. Planned and actual file order were compared from each report's start timestamps.

| A | image crash → image generation | **3 passed / 0 failed / 0 pending** |
| B | image generation → image crash | **3 passed / 0 failed / 0 pending** |

These are **three unique fixture tests sampled twice**, not six unique tests or a full security
acceptance run. Both include the unchanged `before_provider_ack` and `after_capture` SIGKILL
oracles and the generation/rework/delivery journey. Twelve retained daemon stderr files contain
no error/fatal markers; that fact is not proof that every possible execution succeeds.

Two setup failures occurred **before actual samples** and are preserved separately:

1. Passing a sequencer path as a CLI value produced `Sequencer is not a constructor`: zero tests
   collected. The zero-test JSON's `success:true` is not a pass; exit was nonzero.
2. Supplying its constructor through a temporary config hit read-only `/control` when Vite tried
   to write its generated config module. No report/test execution occurred.

The correction made only the authored disposable control directory writable and used an explicit
link to repository dependencies/bare external Vitest import. Product/system mounts stayed read-only.
Both failed setup trees remain in the evidence packet, not hidden by replacement fixtures. An
initial bookkeeping assertion also mistook the root-wide `find` listing of its own redirected
metadata file for nonempty application state; it was corrected to require exactly that metadata
file. No application diagnostic was rerun for that bookkeeping correction.
