### Finding — P1: retained orphan images can strand shared quota without a supported recovery or deletion action

**Location:** `apps/daemon/src/lib/result-retention.ts:38–43`, interacting with `apps/daemon/src/core/repos/results.ts:131–140,186–199,247–253`.

**Reachable proof:** The after-capture SIGKILL test leaves a completed, unreleased image after restart. Its bytes survive, owner reads return 404, and the released library remains empty (`apps/cli/test/image-crash.test.ts:192–213`). The new exemption prevents its previous automatic reclamation. However:

1. Library listing excludes unreleased captures.
2. Detail/download/preview require release.
3. `deleteReleased` cannot delete an unreleased capture.
4. The retained bytes still consume home-wide quota.

Consequently, accumulated orphaned captures can block **all new Result publication**, including ordinary files. The suggested cleanup—“Delete saved results”—cannot remove the hidden captures. Completed images whose delivery is denied or whose hold terminates also satisfy the exemption; this consequence is not limited to crashes.

This is a concrete consequence of the repair, although explicitly acknowledged rather than concealed. It prevents accepting the change as complete image-loss recovery or release-ready functionality.

**Smallest remedy:** retain this bounded storage fix, then add an explicitly approved, operator-owned inventory/recovery/discard surface for the same narrowly qualified captures. Do not restore automatic deletion, auto-release bytes or regenerate images.

### Storage/privacy consequences

The retained content remains private through the inspected HTTP authorization boundary; I found no new disclosure bypass. Its lifetime nevertheless changes: completed private captures survive settled delivery failures and remain in database backups. Backup integrity validation includes every undeleted Result (`apps/daemon/src/lib/backup.ts:45–59`).

The 1 GiB logical-byte limit bounds retained content, not its lifetime or physical SQLite size. Agent deletion/transfer does not itself remove these records; original-Team deletion owns cleanup through the schema. Destructive Team/home removal is not an adequate substitute for a bounded discard control.

## Bounded follow-up recommendation — design only

Use the existing deterministic Result-library delivery semantics, not a worker or conversation replay:

1. **Operator inventory:** expose a bounded inventory of qualified private captures and their quota usage through existing owner authentication. Keep bytes, previews and source transcript unavailable before authorization. CLI and web must use the same daemon contract.

2. **Recover by immutable Result ID:** revalidate the completed-operation match, deletion state, original provenance and current membership. Factor/reuse the authorization sequence in `apps/daemon/src/lib/result-library-delivery.ts:11–28`: shared `authorizeAgentEgress`, `result_library` / `result_publication`, `attemptId = resultId`, and reference-only `agent_result` payload. Release only on allow; use the existing approval dispatcher for approval-required outcomes (`apps/daemon/src/lib/approval-delivery-plan.ts:376–396`; `apps/daemon/src/routes/approvals.ts:432–434`).

3. **Fail closed:** missing, transferred or otherwise ineligible producers must not be replaced with another Agent. Existing release enforces original-Team membership (`apps/daemon/src/core/repos/results.ts:175–183`). Do not reset terminal approvals or fabricate fresh attempt identities to bypass their state. Surface the actual disposition instead of treating the current helper’s swallowed pending/denied exception as recovery success.

4. **Discard independently of disclosure:** an explicit operator-confirmed operation should tombstone eligible private orphan bytes without releasing them. Preserve the completed operation and receipt so retry cannot regenerate or resurrect content. Refuse or explicitly coordinate active producers and live delivery holds.

5. **No model/provider/replay path:** recovery reads only retained bytes; it never sends a generation request, starts an Agent turn, or repeats an uncertain transport delivery.

**Unapproved product choices requiring a bounded decision:** visibility of private-capture metadata, exact recovery/discard controls, terminal-approval handling, and treatment of captures whose original producer is no longer eligible. This review recommends those decisions; it does not grant new authority or approve implementation.

Follow-up acceptance should cover CLI/web parity, policy allow/deny/approval-required outcomes, membership drift, terminal holds, discard races, quota reclamation and crash/restart behavior—without provider calls.
