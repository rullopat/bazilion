## Matrix readiness findings — do not run unchanged

Source: `scripts/migration-upgrade-matrix.mjs` at r4. No code or expectation was changed during
this review. The eight source-supported refusal expectations remain valid; they are still unrun.

### MR1 — child lifetime is not settled before destructive fixture cleanup

`bootDaemon` kills on failed health polling without awaiting `close` (lines 115–118). `stop()`
registers its close listener only when called (124–129), so an already-closed child can leave it
waiting indefinitely. A deadline signal alone is not cleanup confirmation. `finally` deletes the
fixture tree regardless (253), then globally prunes worktrees (254).

**Required before execution:** track spawn/error/exit/close from creation, handle early exits,
bound and await retirement of fixture-owned children before removing their files, retain a blocked
fixture if ownership/cleanup remains uncertain, and remove only the fixture's own worktree metadata.
Never infer cleanup from time, guessed PIDs/groups or a fabricated confirmation; do not introduce
product recovery authority or revive the canceled native/C boundary.

### MR2 — readiness and refusal facts are too weak

The health poll accepts **any HTTP status > 0** (88), including an error response. Refusal is inferred
from an exception string containing `Bazilion cannot start` plus retained sentinel/ledger (236–240),
not an observed startup exit code/signal. A process that prints that text then hangs until killed
can be mistaken for a normal refusal.

**Required:** use the supported health contract, observe actual startup close/exit, distinguish
clean refusal from spawn/network/timeout/forced termination and retain its exact diagnostic. The
0.22 ledger/current canonical-chain count nuance remains: the numeric newer-database guard may
fire before shape comparison. Inspect that actual operator remedy; do not waive it with a generic
substring or weaken production migration guards.

### MR3 — inherited environment and install/worktree effects need containment

Daemon spawning spreads `process.env` (102–109), enables the scheduler, and the harness installs each
old tag's dependency tree (193). Without an outer scrubbed sandbox this can carry operator provider/
account configuration and network access into prior-release code. Current pnpm also need not be
that old release's actual selected manager. Global worktree pruning can affect unrelated metadata.

**Required:** explicit allowlisted fixture environment, isolated HOME/TMP/network/process visibility,
no operator credentials/config/services, and scoped dependency/toolchain/installation authority.
Reconcile how each prior source's pinned tools run before claiming a genuine released-home result.
Do not silently fetch/install or use original daemons/homes under this review authorization.

### MR4 — “home untouched” exceeds current preservation assertions

The script checks a Team sentinel, ledger and absence of migration snapshots, then prints
`home untouched`. It does not compare the paired DB/auth bytes, other files or exact database state;
its inspection opens SQLite without read-only mode (138 onward). This is narrower than the printed
claim and cannot qualify old Results/credentials/backup preservation.

**Required:** bounded before/after fixture preservation evidence, read-only inspection where
appropriate and precise allowed transient-file differences. Failure/refusal must retain authentic
state rather than recreating sentinels or replacing a home. Modelled child tests alone are not a
pass of the genuine-home matrix or installed artifact.
