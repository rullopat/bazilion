### Finding: P1 — Failure retention occurs after destructive uninstall

**Location:** `scripts/installer-e2e.mjs:60–63,629,797–807,813–821`.

`fail()` only appends a failure. For example, a failed new browser-diagnostic assertion at line629 continues through normal shutdown and unconditional `uninstall --yes` at line799. The failure status is applied only afterward, at line807.

Consequently, final cleanup retains the fixture root, but the primary DB, auth pair, agents and transcripts have already been removed. The retained successful uninstall output confirms those exact paths are deleted. This contradicts the new failure-retention contract in `docs/testing/0.23.0-guarded-installer-20261019.md:42–43`.

A related reachable path exists when coding-provider retirement requires SIGKILL: non-graceful `stop()` returns `forced:true`, while `closeAll()` rejects it only after uninstall (`scripts/testing/installer-process.mjs:42–48,72–79`; installer line293).

**Smallest remedy:** before destructive uninstall, require no accumulated functional failures and acceptance of all preceding owned-close outcomes. Otherwise throw into the retaining finalizer. Preserve the successful uninstall oracle. Add controlled tests proving assertion failure and forced retirement cannot reach uninstall.

### Finding: P2 — Removal failure leaves retained JSON claiming success

**Location:** `scripts/installer-e2e.mjs:821–858`.

The report serializes `passed:true` before `rmSync(fixtureRoot)`. If removal throws, the process correctly becomes nonzero, but an external evidence file still says `passed:true` with no cleanup error.

**Smallest remedy:** record fixture-removal outcome explicitly and ensure retained external evidence reflects a removal failure. Test the removal-error path without invoking real installer dependencies.

### Finding: P2 — New SSR response capture lacks a byte bound

**Location:** `scripts/installer-e2e.mjs:532–543`.

The SSR fetch has a two-second signal, but `login.text()` buffers the complete response without a byte ceiling. The process-output cap does not cover HTTP response bytes. Thus the new SSR seam is time-bounded but not output-bounded.

**Smallest remedy:** consume the body with a modest explicit byte limit, cancelling and failing when exceeded. Preserve the existing status/content oracle and deadline.

- **Merge verdict:** **BLOCK** pending the P1 retention correction. P2 items are report-only notes.
